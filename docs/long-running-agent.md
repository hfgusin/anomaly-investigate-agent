# 长任务运行（总路线图 P2 Agent Runtime）

总编号见 [P0～P13 路线图](roadmap.md)。本文 LR-* 仅表示长任务内部步骤，替代早期与总路线图冲突的 P1-* 编号。

## LR-1：步骤事件与检查点（已实现）

每条 Run 在原有 `runs` 表中增加 `checkpoint`，并在 `runEvents` 表中按 Run 保存连续 `seq`。接受、开始、工具请求、审批、执行、结果、引导和终态的事件与对应 Run 状态在同一 SQLite 事务写入。事件只保留工具参数和结果的 SHA-256、长度等元数据；完整工具记录仍在 `toolTrace`。页面在 Run 状态旁显示当前步骤，展开运行记录可看到检查点序号和已完成工具数；Gateway 的 `runs.events({runId})` 可读取完整步骤顺序。

运行记录展开后可刷新并查看每条步骤事件。旧库自动增加新表和列；旧 Run 没有历史步骤事件，不会伪造旧记录。

## LR-2：`/research2` 恢复执行（已实现）

Gateway 启动时只把未完成的 `/research2` Run 重新排队；其他运行继续沿用 `interrupted` 终态。正常停止 Gateway 时，这类研究 Run 也会先挂起，供下次启动恢复。恢复器从 `toolTrace` 重建本轮的搜索次数、打开次数、候选标题和已打开句子。已完成且落库的调用不会重新执行；执行中但尚未落库的只读调用保留原审批，恢复后重试。原部分模型输出保存到 `runAttempts`，新的回答从空输出开始，并把已保存工具结果作为不可信数据送入新模型请求。模型网络流不能原地续传；再次请求可能产生不同措辞和额外模型费用。恢复证据长度及次数写入 `contextTrace`。

## LR-3：审批与终态（已实现）

重启前仍在 `requested` 的工具保持待审批，在页面重新显示允许/拒绝；不会自动批准。此前已批准且执行中的只读工具可重试。拒绝后不执行工具；取消后的 Run 不进入恢复队列。第一版没有有副作用工具的自动恢复。

## LR-4：故障注入与真实模型验收

受控自动检查分别在工具开始、工具结果返回但未提交、结果和检查点已提交后 `SIGKILL` 进程；恢复后每次只留下一个已完成工具事件，已提交结果不重做，未提交只读步骤才重试。正常关闭时等待审批的研究 Run 也可恢复。另一次真实模型检查在首条搜索结果落库后强杀 Gateway，重启后同一 Run 完成四次工具调用并给出带两篇出处的回答。原始报告在本机 `.data/hotpotqa/resume-live-check.json`。这证明该场景的续跑链路，不证明所有长任务或回答准确率。

用户页面验收：重启正在执行 `/research2` 的 Gateway 后，刷新页面应看到同一 Run 的步骤检查点、恢复次数和步骤事件；若停在工具审批，仍由用户点允许或拒绝。再次回答可能不同；检查是否复用了之前已完成的工具事件，而不是只看最终答案。

## 协作任务恢复

现已扩展到带 Agent 配置快照的 `/team` 父任务及其只读孩子：恢复同一批子 Run，复用已完成结果，保留待审批状态，并取消父任务已经结束的遗留孩子。父子关系、并发与真实强杀验收见 [Multi-Agent](multi-agent.md)。
