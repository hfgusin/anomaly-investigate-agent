# 自动化运营 Agent：功能规划

记录日期：2026-10-04

状态：已讨论的候选方案，尚未实施。实施顺序为建议，不代表已确认全部开发范围。

## 目标

围绕已有广告自动化，帮助用户看清执行、发现差异、验证规则修改。

首个功能：用户提供 Airflow DAG ID、GSheet 规则、业务日志表或 SQL，Agent 生成可检查证据的动态看板。

动态同时包含两层含义：

1. 数据随新的 DAG 运行和业务日志持续更新。
2. Agent 根据不同自动化任务，选择合适的指标、图表和对象明细。

## 三类数据来源

| 输入 | 获取方式 | 主要用途 |
| --- | --- | --- |
| Airflow DAG ID | 已有 Airflow API 查询工具 | 运行状态、任务状态、运行时间与技术错误 |
| GSheet 规则 | 待确定规则 Sheet 的读取方式 | 业务条件、动作、阈值和规则版本 |
| 日志表或 SQL | DI Livy 执行 SQL | 实际处理对象、指标、动作、操作结果与业务异常 |

这里的业务日志通过 DI 查询 Hive 表，不要求用户提供本地日志文件。Airflow 的任务日志与业务操作日志分别保留，不混为同一类证据。

用户提供的日志查询示例：

```bash
di livy +sql --mode interactive \
  --sql "SELECT * FROM cnfashionbi_scs.scs_ads_roll_out_rab_roas_data LIMIT 10" \
  --queue cnfashionbi-dev \
  --service-env sg
```

以上是用户提供的入口记录，当前未执行、未核对 CLI 语法或表结构。`LIMIT 10` 适合查看字段和样例，不足以支撑完整执行统计。正式查询需要明确时间范围、运行标识、筛选条件和数据量限制。

## 1. 动态执行看板

### 用户流程

1. 用户提供三项数据入口。
2. Agent 读取字段与样例，识别任务类型和可用关联字段。
3. 生成看板草稿，展示对规则、日志字段和指标口径的理解。
4. 用户确认后保存看板配置，持续刷新数据。
5. 规则或日志结构变化时，Agent 提出配置调整，用户确认后更新。

### 固定内容

- 最近运行：成功、失败、执行中，以及数据更新时间。
- 执行汇总：处理、跳过、失败数量；统计口径明确区分对象数量和日志行数。
- 对象明细：商品或广告、对应指标、规则、动作和结果。
- 证据入口：规则原文、业务日志记录、对应 Airflow 运行。
- 数据状态：读取失败、数据尚未到达、成功查询但为空、关联失败分别展示。

### 按任务生成的内容

| 任务类型 | 看板重点 |
| --- | --- |
| 调预算 | 调整前后预算、触发指标、命中规则、调整金额 |
| 暂停广告 | 暂停对象、触发条件、接口结果 |
| 创建广告 | 创建数量、广告 ID、创建参数、失败原因 |

普通刷新沿用用户确认的看板结构，不在每次刷新时重新生成布局。缺少字段的指标显示“无法计算”，不补造数据。

### 首版验收目标

选一个用户熟悉、日志较完整的 DAG，实现一张真实看板。能从一条执行记录追到对应规则和运行；关联不了的记录明确标记。新的运行出现后更新数据，保留已确认的展示结构。

## 2. 执行对账

### 要解决的问题

核对“按规则应该执行什么”与“实际日志记录了什么”，发现执行差异。

### 候选检查

- 命中规则，但缺少执行记录。
- 同一个广告在约定的去重范围内重复加减投。
- 日志记录了拟调整动作，但接口返回失败。
- 实际预算调整比例与规则不一致。
- Airflow 显示成功，但业务日志存在部分失败。

每个异常应附对象、运行标识、规则证据、指标和日志记录。日志若只记录已执行对象，不能据此发现所有“应该执行但没执行”的对象；该检查还需要候选对象与当时指标快照。

### 首版验收目标

选取字段足够支持的一类对账，能展示差异及其证据。未满足数据条件的检查标记“无法核对”，不把缺失记录自动判为执行失败。

## 3. 规则试跑：fake 加减投

### 要解决的问题

用户修改规则前，先看新规则会影响哪些广告或商品。试跑不操作广告账户。

### 示例交互

用户提出：把“ROI < 1 时减投”改成“ROI < 1.2 时减投”。

试跑展示：

- 原规则与修改后的规则。
- 新增命中、退出命中和动作改变的对象。
- 每个对象的实际输入指标、命中条件与拟执行动作。
- 基于已知预算计算的拟调整前后金额与合计。
- 实际修改账户次数为 0。

### 实现职责

- Agent：理解用户修改，提出规则草稿，组织试跑，解释差异。
- 确定性代码：验证规则、执行条件判断、计算预算与结果差异。
- 试跑执行器：使用隔离的模拟操作接口，不调用真实账户写入接口。

只有日志表而没有足够的输入指标时，不能承诺完整试跑。需要先确认能否获得当时的候选对象、指标、原预算及必要的账户约束。

### 边界与验收

试跑用于检查规则影响，不预测调整后的真实 ROI、销售额或投放效果，不用虚构效果证明策略有效。规则修改与试跑结果可追溯，真实账户无副作用。

## 4. 失败排查

### 示例问题

“今天这个 DAG 为什么失败？影响了哪些商品？”

### 排查链路

读取对应 Airflow 运行及任务错误，再通过 DI 查询匹配的业务日志，区分：

- 任务启动失败。
- 数据读取失败。
- 规则处理失败。
- 广告操作部分失败。
- 日志保存失败。

输出已确认的失败证据、可确认的影响范围和下一步检查项。把已确认原因、推断和未知分别写明。首版只读排查，不自动触发 DAG、重跑任务或补执行广告操作。

### 首版验收目标

能解释一次真实失败并指向证据；没有足够业务日志时明确说明影响范围未知。DAG 成功时仍能发现已记录的业务部分失败。

## 5. 历史回放

### 示例问题

“昨天为什么给这个广告减投？”

展示当时输入指标、当时规则、拟执行动作、接口结果和对应运行。

需要保存规则版本或快照，以及足够的历史输入数据。当前 Sheet 内容不能冒充历史规则。资料不全时仅展示已知事实，不强行还原完整判断过程。

## 建议实施顺序

1. 动态执行看板：打通三类数据，确认关联方式。
2. 执行对账：先实现数据能支持的一类差异检查。
3. 规则试跑：复用已确认的规则和指标，隔离真实写操作。
4. 失败排查：关联 Airflow 技术错误与业务执行结果。
5. 历史回放：在规则版本、指标快照具备后实现。

## 开发前需要确认的事项

- 第一个 DAG 及规则 Sheet 的具体入口与范围。
- 日志表字段、时间字段和日志到达延迟。
- 是否有 DAG run ID，如何关联一次运行与业务日志。
- 商品、店铺、广告的唯一标识与去重范围。
- 日志能否区分候选、跳过、拟执行、实际执行和接口成功。
- 规则是否有稳定 ID 与历史版本，是否允许保存快照。
- DI 的认证、查询结果格式及返回量限制；GSheet 的读取凭据。
- 看板刷新频率和刷新范围，避免反复扫描全表。
