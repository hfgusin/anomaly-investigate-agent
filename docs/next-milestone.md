# 下一大阶段：把一次检索改成可审计的多跳研究 Agent

## 要解决的问题

当前 `/research` 在一次 `research_hotpot` 工具调用里完成两跳检索，再由模型一次性回答。它已经能用公开资料作答，但模型无法根据首跳结果选择下一篇文章；返回了证据仍可能选错实体、漏引句子。固定 10 题的新模型联合精确匹配只有 3 题。下一阶段的目标是让模型真的逐步选择资料、允许有限纠错，并用未参与调试的题验证结果。

## 执行顺序和交付

1. **先验证工具协议。** 用新模型实际完成“搜索 → 打开文章 → 再打开关联文章 → 回答”的至少两轮标准 `tool_calls`/`tool` 消息。记录原始事件、每轮工具调用、错误和耗时。只有稳定通过后才把本机研究任务从 `plain` 切到 `standard`；旧模式保留为显式兼容选项。
2. **拆开研究工具。** 将目前的一次性 `research_hotpot` 拆为 `search_passages(question)` 与 `open_passage(title)`。搜索只返回候选标题及短片段，打开文章才返回带 `Title#sentId` 的句子。候选范围固定为该题的 10 篇 HotpotQA distractor 文章；标准答案和支持事实只供评测使用，绝不进入模型请求或工具结果。
3. **加入有界研究循环。** 一个 Run 最多 2 次搜索、4 次打开文章和 1 次修正回答；每次工具参数、结果、引用来源和终态写入现有 Run trace。模型若无足够证据可明确回答“证据不足”；超时、拒绝和 Worker 重启不能悄悄重放已可能执行的操作。
4. **校验回答与有限修正。** 最终输出解析为短答案和引用集合；检查每个引用是否来自已打开文章、是否覆盖必要的两个检索跳点。若格式或引用错误，给模型一次具体错误反馈后重试；仍失败则保留原文并以失败终态结束。校验器不读取标准答案，也不宣称能判断语义正确。
5. **评测和用户验收。** 先固定开发题集，再从未用于调试的 hard bridge 题中固定抽取 100 题作为最终样本。保存题目 ID、数据哈希、模型名、模式、原始输出、工具轨迹、答案 EM/F1、支持事实 EM/F1、联合指标、错误率和耗时。以同一模型、同一题集、同一配置下的当前单工具流程为基线；目标是在 100 题上联合 EM 至少多 5 题，且无证据引用与工具失败率不能变差。若没达到，就记录失败而不宣称改进。用户可在页面验收一题成功链和一题证据不足链。

## 技术深度的展示材料

交付可重放的逐步工具 trace、失败分类（检索缺证据、选择错实体、格式/引用错误、接口错误）、同题集对照结果和故障恢复记录。面试时可以沿一条真实失败 Run 解释：模型看到了什么、选择了什么、运行时拦住了什么、修改后指标如何变化。

第一步的停止条件很明确：如果新模型不能稳定完成多轮标准工具消息，先定位协议或服务商问题；不能用单轮成功假装完整 Agent 循环可用。

## 第一步当前进度

已增加 `node scripts/check-model-multiround.mjs` 诊断脚本。它给模型两个有依赖的只读工具：先 `find_source` 返回运行时随机 ID，再 `read_source` 用该 ID 返回随机代号。新模型在 5 次独立试跑中均按顺序调用两次工具，并准确回答代号；记录在本机 `.data/model-multiround-standard*.json`。这证明标准工具消息能跨两轮往返；该诊断本身只用合成资料，不代表下面的真实研究结果。本机 `.env` 仍保持 `plain`，实验入口按 Run 覆盖为 `standard`。

## 第二版当前实测（实验入口）

`/research2` 已通过真实 Gateway 串起标准工具消息、审批、Worker、SQLite 工具记录和两篇出处校验。`search_passages` 返回五篇候选标题与短片段，`open_passage` 返回带句号的全文；模型可在两次搜索和四次打开文章内选下一跳。出处不足时运行时给一次具体校验反馈，修正草稿与结果写入 Run 的 `contextTrace.researchRepair`；受控回归证明修正后可打开缺失文章并完成。真实模型的集数题这次初稿已有两篇出处，未触发修正，不把受控回归写成真实修正成功。

固定的开发诊断 10 题用 `node scripts/eval-hotpot-v2.mjs <题目 ID>` 逐题试跑，原始记录保存在本机 `.data/hotpotqa/v2-current-*.json`。这条 CLI 路径不经过 Gateway 的一次修正。结果：8/10 完成引用校验，答案 EM 3/10，支持事实 EM 5/10，联合 EM 1/10；39 次工具调用中 3 次返回限额错误。旧 `/research` 在同一固定题集的最近记录为答案 EM 5/10、支持事实 EM 6/10、联合 EM 3/10。两种流程提示和检索方式不同，模型输出也有波动；现有结果明确不足以替换默认入口。

已知失败：`UFC 50` 经稀有词和连续词组排序进入候选，模型找齐标准支持句，但把标准答案 `The War of '04` 输出成完整赛事名 `UFC 50: The War of '04`，严格答案 EM 为 0；另一题模型答对 94 却只引用一篇文章，CLI 校验失败。工具结果现明确返回 `remainingSearches` 和 `remainingOpens`。对两道曾超出搜索次数的题复测，其中一题不再发起第三次搜索，但答案仍错；另一题仍发生一次打开文章错误，不能宣称余量提示已解决规划问题。Gateway 路径的配对结果见下。

## Gateway 配对评测：固定开发题 10 题

`node scripts/eval-hotpot-gateway-paired.mjs` 已用同一模型、同一 validation 文件、同一固定题 ID 经真实 Gateway 成对运行 `/research` 与 `/research2`。每题独立会话；只自动批准该评测自身的只读研究工具；奇偶题交替运行顺序。数据 SHA-256、模型、输出、工具 trace、修正记录、状态、耗时和逐题分数保存在本机 `.data/hotpotqa/gateway-paired-2026-09-30.json`。标准答案和支持事实只在 Run 结束后计分，没有传给模型。`answerEM`、`supportEM` 和 `jointEM` 只计 Gateway 完成的 Run；失败草稿另保留在逐题记录里。

| 指标 | `/research` | `/research2` |
| --- | ---: | ---: |
| Gateway 完成 | 7/10 | 9/10 |
| 答案 EM | 5/10 | 4/10 |

新版多完成了两题，联合 EM 仍低一题且耗时约三倍，不能替换默认入口，也不能以这 10 题宣称整体效果。典型失败：`José Baviera` 题在打开首跳前用尽两次搜索，随后 `open_passage("Luis Buñuel")` 因标题不在候选而失败，最终只能答“证据不足”；Garth Brooks 题已打开三篇文章，但初稿和唯一修正稿都只引用 `Sevens (album)`，被两篇出处校验拒绝。下一步先针对搜索预算分配和修正反馈做开发题诊断，再封存实现进入未参与调试的 100 题最终评测。
