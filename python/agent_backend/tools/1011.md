不够 Agent 的部分

现在 ads-check 的步骤是写死的：查运行状态，查任务状态，跑总览 SQL，跑分类 SQL，写报告。模型在里面主要做两件事：把你的话翻译成日期，再把结果写成中文报告。查什么、按什么顺序查，都是我们提前定好的。这种东西叫 workflow（工作流），不叫 agent。

workflow 本身没错。很多场景下它比 agent 更稳定、更便宜，业界也普遍建议能用 workflow 就别硬上 agent。问题只在面试：别人问"为什么需要 Agent"，你得有答案。

两者的区别，用你的数据举例

拿 10-06 来说，PH 有 16 行 get_roas_fail，比其他站点多很多。

workflow 的做法：在报告里写一句"PH get_roas_fail 16 行"，然后结束。
agent 的做法：注意到这个数字异常，自己决定往下查。
先对比前 7 天：如果 PH 每天都这样，是老问题；如果是今天突然冒出来的，就是新问题。
如果是新问题，再看这 16 个商品有没有共同点，比如是不是同一批活动、同一个操作类型。
再去读 Airflow 日志里对应的报错行，或者对比规则配置有没有变化。
最后给出"可能原因 + 证据 + 还需要谁确认"。
每一步查什么，取决于上一步看到了什么，没法提前写成固定 SQL。这就是"真正需要 Agent"的部分。

所以接下来不用推倒重来，在现有基础上加一层"发现异常就自己追查"就行：

把现在固定的总览和分类查询保留下来，当作第一步。
加一个"基线对比"的能力：同样的查询跑前几天，算出哪个站点、哪类失败是异常。
在 Skill 里告诉模型：遇到异常时可以自己决定往哪查，但要控制查询次数，并且每个结论都要有证据。
面试时可以这么讲："先用 workflow 把可靠的部分固定下来，只在需要判断的地方交给模型。"这比"全部交给 Agent"更有说服力，也正是现在业界推荐的做法。
