# Agent 岗位能力对照与作品集补强计划

核对日期：2026-10-15。依据当前源码、工具注册、配置和已有报告。只评价项目能提供的证据，不能仅凭 AI 辅助完成的代码判断个人能力。

## 对 JD 的判断

这份 JD 可以作为目标，但“三年经验”不能机械等同于每一项都已独立做过。对该岗位有说服力的是：能独立完成一个有业务价值的 Agent 闭环，说明技术取舍，用评测证明效果，并能定位真实失败。RAG / Agent / Fine-tuning 至少精通一项，不要求为了覆盖关键词再补一次微调。

L3–L4 的等级定义未随 JD 提供，暂不自行贴等级。本项目用可验收的任务拆解能力对齐：子任务有输入、依赖、工具、产出、验证、失败出口和人工决策点；后续按招聘方的等级口径解释。

## 补强顺序与每步完成条件

### M1：业务来源映射 + 商品操作追溯单 Agent 闭环

已落地第一步：[业务来源查询](business-sources.md)。`/source-lookup` 配合只读 `search_business_sources` 按需读取原文目录；支持任务名、描述和业务别名检索，未知表名不推导，尚未建立向量索引。DataMap/DataHub 发现、完整来源口径和真实商品操作闭环仍待完成。

把 `script_and_data_info_record.md` 作为人工业务说明输入；空 taskId 已改为 null，读取时校验字段类型，但不能把类型通过当作业务核实，不自动补造缺失信息。

建议用 Pydantic 校验来源记录：来源 ID、表完整标识和 IDC、用途、主键/粒度、站点字段、业务时间/时区、分区、动作/结果枚举、生产任务、源码路径、已核对证据、待确认项。未知信息用 null，不强制猜值。决策、操作请求、接口回执、GSheet 留底是不同证据层。

候选搜索读取 DataMap，任务详情读取 DataHub；工具元数据仍只注册在 Python。表名与 DataHub 任务名分开存，不能假定完全相同。搜索结果是候选，不直接成为可信映射；采用映射前保留人工核对。

第一批 3–5 个异构来源，至少覆盖指标/快照、规则/决策、实际操作。工作流：确定 item/站点/时间 → 选来源 → 看 schema → 构造有日期约束的查询 → 区分请求/成功/fake → 找实际脚本证据 → 时间线。缺站点时可先找已接入来源，存在多个匹配则分别展示或澄清。

完成条件：至少 10 个可复现开发例中，来源选择、时间口径、成功/fake/失败区分和证据链接都经人工核对；同 item 多站点不串；查不到与查失败不混淆；不能仅以相近任务时间确定脚本。此数量仅是开发门槛，不作为 90% 质量证明。

### M2：把正确率、证据和业务收益测出来

从 [12 个合成开发例](../portfolio/evaluation/cases.json) 起步；gold 仅评分时读取，不能送给模型。随后增加独立写作的开发样本和未参与调优的封存样本，按问题族、来源、时间窗口隔离，避免同一个案例改 item ID 就跨进训练/测试两组。

业务测试集建议至少 100 个封存样本，覆盖正常、歧义、无数据、工具失败和不可验证情况；权限不足等 case 的正确结果可以是明确不可验证，但必须单独统计，不能靠大量拒答提高回答正确率。模型、提示、Skill、数据和代码指纹冻结，每次报告写分母、失败、弃答和缺失评分。

指标：

- 端到端正确完成率 = 经人工规则确认答案/正确澄清/正确不可验证的 case 数 ÷ 全部发起 case。模型中断或未输出不算完成。另报可回答题的答案正确率与回答覆盖率，防止拒答套利。
- 无依据事实率 = 已审查输出中无证据或与证据冲突的可核验事实数 ÷ 全部已审查可核验事实数；无法判断的标 unknown，公开 unknown 占比，未完成审查不能宣称达到阈值。另报“含至少一个错误事实的任务占比”，避免用大量正确小事实稀释严重错误。
- 引用支持率、来源选择准确率、正确澄清/拒答率分别报告。
- 模型/工具耗时与人工审批等待分开，报 p50/p95；费用按实际供应商 usage 和版本价格计算，缺失 usage 标 unknown。
- 同题人工流程对照：从找表到核对并形成结论的人工有效分钟数、返工率与总等待，配对统计中位数；不预填节省百分比。

90% / 5% 是拟验收目标，不是既有结果。100 例的点估计不是稳定保证，需要报告置信区间；生产分布变化后继续抽查。

### M3：有理由地接入 RAG

业务字段/规则说明与公共投放知识分开索引，保留来源、版本、生效时间和适用站点。优先为“哪个规则是什么意思/应核对什么”提供证据；实际商品何时操作必须查操作记录，不能由知识库代答。

接入一个只读检索工具，保留现有 dense/BM25/RRF 通道信息。用标注题比较 BM25、dense、hybrid 的 Recall@k / MRR 和答案支持性；先定位漏召回还是错误排序，再决定是否加 reranker。拒答阈值用开发集校准，RRF 分数不能当正确概率。

完成条件：相同封存题集对比检索方案；可展示至少一个检索失败及改动理由；知识缺失时不套用其他站点/时间的规则。主 Agent 只有需要文档证据时才检索。

### M4：业务 Multi-Agent 和可观察的计划

先保留单 Agent 基线。业务计划按步骤保存目标、依赖、来源、状态及证据 ID；工具错误、缺信息时能更新计划或转人工。

只有相互独立时才并发，例如“任务日志/源码核对”和“已知候选表 schema/数据核对”；SQL 依赖 schema，不并行猜 SQL。业务子角色需要扩展当前只允许 reader/researcher 工具的配置校验，不能只改 agents.json 提示词。

子任务返回结构化事实、证据、未验证项和错误类型；汇总者核对站点、时间、ID 和冲突，不默认接受每个子任务的结论。复用现有父子 run/key、并发和审批。

完成条件：同一批题、同一模型配置，比较单 Agent 与协作的端到端正确率、耗时、调用数、费用；测一个孩子失败/停在审批/重启。没有收益时保留单 Agent，作品集展示这一取舍本身。

### M5：模型路由与可交付运维

先采集任务类型/难度/工具错误标签及实际 usage。用大模型离线辅助标注，由人工修订；简单抽取/翻译尝试小模型，证据冲突或 schema 歧义升级强模型。升级不自动重复业务写入。没有第二模型配置时先保留单模型，不伪造路由收益。

同题比较单强模型、单小模型和路由三组，质量达门槛再看成本与 p95。成本只能用真实 token usage、缓存费用和价格版本计算；缺数据不估成 0。

先交付无需公司凭据的合成 demo adapter、依赖锁定与启动文档、自动化工程回归及一段演示；再根据实际多人部署需求补身份/权限、隔离、备份恢复演练和服务监控。当前所有本地 SQLite、限流和恢复设计都应说明单进程边界。

## 作品集材料与本人参与

- 案例：一次数据来源误判、一次工具超时/重启、一次拒绝写入、一次无法确认历史状态。每个案例讲证据、改动、验证和剩余问题。

- 实操验收：独立增加一个只读来源工具、修一个参数或返回类型 bug、从 trace 复现一个错误并补一个有效行为测试。能完成这些比记住框架名更能证明三年工程经验。
